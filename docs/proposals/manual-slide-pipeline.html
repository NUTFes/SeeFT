マニュアルの現状の運用と課題

技大祭のマニュアル類は Google Document で作成。配布は SeeFT のモバイルウェブ（シフトページ）に Google Doc の URL を貼り付け、当日担当者がそこからリンクをタップして Google Docs で閲覧する運用。

現状の運用フロー

1担当者が Google Doc でマニュアルを編集 ↓ 2PM・担当者が SeeFT モバイルウェブのシフトページに Doc の URL を登録 ↓ 3当日担当者が SeeFT モバイルウェブを開く ↓ 4自分のシフトページに表示された Doc リンクをタップ ↓ 5Google Docs（ブラウザ or アプリ）で Doc を閲覧 ↑ ここがスマホで読みづらい

Google Docs をスマホで開いた時の課題

閲覧体験の問題

  • Google Doc は PC 想定の縦長レイアウト。スマホ縦持ちで段落構造が見にくい
  • Doc 内の目次があってもスマホアプリだとジャンプ動作が安定しない
  • 緊急連絡先までスクロールが長い。必要な時に到達に時間がかかる
  • 電話番号がプレーンテキストだと タップで発信できない
  • 画像が小さくて、いちいちタップして拡大しないと見えない
  • 長尺 Doc はスマホでロード・スクロールが重い
  • 「自分のチームのやること」を Doc 全体から探すのに時間がかかる

運用上の課題

マニュアル管理側の困りごと

  • 各局・部門でフォーマットがバラバラ、見た目が統一されない
  • 当日「どこに書いてある?」の問い合わせが発生
  • 運用責任が SeeFT 側じゃなく Google Doc 側に流出している（編集権限・閲覧追跡など）
何をしたいか（ビフォーアフター）

Google Doc を「スマホで見やすい解説 Web ページ」に自動変換するツールを運用したい。シフトページから飛ぶ先を、Doc URL から 生成された Web ページ URL に置き換える。Doc の編集作業は変わらない。

提案後の運用フロー

1担当者が Google Doc でマニュアルを編集（変わらず） ↓ 2PM が ツールを実行して解説 Web ページを生成 ↓ 3PM が生成された Web ページの URL を SeeFT シフトページに登録（Doc URL の置き換え） ↓ 4当日担当者が SeeFT モバイルウェブを開く ↓ 5自分のシフトページに表示された Web ページリンクをタップ ↓ 6スマホ最適化された解説ページで閲覧（カード形式・タップ操作）

完成イメージ

生成される解説 Web ページの主な機能。

  • カード形式 UI: 情報の塊が視覚的に分離、一目で何の情報か分かる
  • 役割ごとのカード: チーム A の担当者は A のカードだけ見れば「担当場所・必要物品・指揮者・関連資料」がすべて揃う（カンバン形式）
  • 目次ボタン: 上部 + 右下のフローティングボタンから、どこからでも目次に戻れる
  • 章末「次へ」リンク: スクロール下方から自然に次章へ進む導線
  • 電話番号タップで即発信: <a href="tel:..."> で確実にリンク化
  • 画像タップで拡大: ライトボックスで全画面表示
  • スマホ縦持ち最適化: 文字サイズ・余白がスマホで読みやすい
  • 1ファイルに完結: 画像も含めて単一 HTML、URL 1つで配布

生成のしくみ（パイプライン）

担当者・PM・受け取り手の役割を3ステップに分けるとこうなる。

1

マニュアルを書く

担当者（従来通り）
  • Google Doc でマニュアル本文を書く
  • 手順写真・配置図を貼る
  • 連絡先・必要物品を記載
  • 作業内容は変わらない
2

ツールが Web ページを生成

PM（コマンド1回、3〜6分）
  • Google Doc を HTML エクスポート
  • ツール（uv で動く Python スクリプト）を実行
  • 内部で Claude (Anthropic) を呼び、Doc を解釈・整形
  • 画像はプレースホルダーから base64 で埋め込み
3

Web ページを SeeFT に登録

PM が登録 → 受信者が閲覧
  • 生成された Web ページをホスティング
  • SeeFT シフトページの URL を Doc → Web ページに更新
  • 当日担当者は普段通り SeeFT を開けばリンクが置き換わっている

内部パイプライン詳細

[Google Doc] ↓ HTML エクスポート（手動） [ソース HTML + images/] ↓ pandoc で Markdown 化 ↓ 正規表現で Google Docs のノイズ除去 [クリーン Markdown + 画像ファイル名リスト] ↓ system_prompt = .claude/manual-prompt-card.md（カード形式の出力規約） ↓ user_prompt = Markdown + 画像リスト ↓ Claude Opus 4.7 を呼び出し（サブスク認証経由） [HTML（画像は {{filename}} プレースホルダー）] ↓ 後処理: プレースホルダーを base64 で置換 [slide_xxx.card.html（自己完結、画像内蔵）]

共通プロンプト .claude/manual-prompt-card.md でカラー・章構造・カンバン要件を一元管理。プロンプト改善が全マニュアルに自動波及する設計。

何が嬉しいか

当日担当者にとって

  • スマホ縦持ち最適化で段落構造がはっきり見える
  • 自分のチーム情報がカード1枚で完結
  • 緊急時の連絡がタップ1つで発信
  • 画像も大きく拡大して見られる
  • 長尺 Doc のロード重さがない（軽量 HTML）
  • 事前ダウンロード済ならオフライン閲覧可

各局・部門にとって

  • 担当者の Doc 編集作業は増えない
  • マニュアル更新時の再配布が再生成→URL 入れ替えで済む
  • 配布が1ファイル化、誤共有リスク低減
  • 各マニュアルの見た目・操作性が統一される

マニュアル管理者・PM にとって

  • 「どこに書いてある?」問い合わせが減る想定
  • 過去マニュアルも同じ仕組みで再生成可能
  • 共通プロンプト改善で全体品質を一括引き上げ
  • 運用責任を SeeFT 側に取り戻せる（Doc 外部依存の縮小）

執行部に確認したいこと

今後の運用を進めるうえで、執行部に判断してほしい事項。

1

Claude サブスクの経費処理

月額 3,000〜14,000 円程度。PM が個人契約 → 経費精算 で進めて OK か。組織で一括契約する場合は別途相談。

2

生成された Web ページのホスティング先

選択肢: GitHub Pages / SeeFT のサーバーに静的ホスト / S3 などの外部ストレージ / その他。各案のメリット・運用負担を比較して決めたい。

3

SeeFT シフトページの URL 入れ替え運用

Doc URL から Web ページ URL に切り替えるタイミング・手順・責任者を決めたい。新旧並列期間を設けるかどうかも。

4

マニュアル原本（Google Doc）の管理ルール

誰がいつ更新するか、PM が原本を再エクスポートするタイミング、更新通知をどう PM に届けるか。

5

次期 PM への接続タイミング
