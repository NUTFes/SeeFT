このドキュメントについて

本ドキュメントは 解説マニュアル自動生成パイプライン の運用を引き継ぐ新 PM 向けの技術リファレンス。

  • 対象読者: 次期 PM（前任 PM = 上林 から引き継ぎ予定の人）
  • 前提知識: Mac/Linux のターミナル操作、Homebrew、Git、簡単な Python の存在認識程度
  • 執行部向けの非技術的な提案資料は別 HTML（manual-slide-pipeline.html）を参照

このドキュメントの位置付け

「執行部向け説明資料」は なぜ・何をしたいか にフォーカス、こちらは どう動かして何に注意するか にフォーカス。両者は読者層も目的も異なる。

引き継ぎ前に揃えるもの

必須環境

  • macOS または Linux マシン
  • Homebrew インストール済
  • 本リポジトリのクローン (git clone 済)
  • Claude Pro または Max のサブスク契約（個人または経費精算）

セットアップ手順（初回のみ）

brew install pandoc uv # Claude Code CLI のインストールとログイン claude login # ブラウザが開いて OAuth フロー、サブスク認証

依存パッケージのセットアップ

各バックエンドは uv で独立した Python 環境を持つ。初回のみ自動セットアップされる。

# 各バックエンドの依存セットアップ（初回のみ） cd scripts/sakura-slide && uv sync cd scripts/claude-slide && uv sync
パイプライン技術構成

データフロー

[ Google Doc ] │ Drive で「HTML エクスポート」（手動） ▼ [ ソース HTML + images/ ] ← docs/manuals/<name>/ に保存 │ │ Step 1: pandoc で HTML → Markdown │ + regex で Google Docs ノイズ除去（{style="..."}, {.cN}） │ ▼ [ Markdown text + 画像ファイル名リスト ] ← ディスク保存なし、メモリ上 │ │ Step 2: LLM 呼び出し（3バックエンドから選択） │ system_prompt = .claude/manual-prompt-card.md │ user_prompt = MD content + 画像ファイル名 │ ▼ [ HTML with {{filename}} プレースホルダー ] │ │ Step 3: replace_placeholders() で画像を base64 化して埋め込み │ ▼ [ slide_xxx.card.html ] ← 自己完結、画像内蔵

設計上のポイント

  • 3バックエンドが同じプロンプトを参照: プロンプト改善が全バックエンドに自動で波及
  • 画像配置は LLM、base64 化は後処理: LLM の責務最小化、画像処理は決定的
  • 中間 Markdown はディスクに残らない: デバッグ時に確認したければ別途保存ロジック追加要
  • CSS/JS は LLM 生成: プロンプトの指示で <style> 内に組み立てる
3バックエンド比較

同じプロンプトを使う3種類の LLM バックエンドを用意し、状況に応じて使い分ける。

バックエンドスクリプト認証画像入力モデルコスト主用途
Anthropic API scripts/generate_manual_slide.py ANTHROPIC_API_KEY 環境変数 vision あり（base64 inline） Claude Opus 4.7 従量課金（$0.5〜1/本） 組織で API 契約済の保険
Sakura AI Engine scripts/sakura-slide/generate_slide.py SAKURA_API_KEY 環境変数 vision なし（モデル制限） gpt-oss-120b 従量（API より安） バルク・コスト最優先時
Claude Agent SDK scripts/claude-slide/generate_slide.py claude login サブスク認証 vision なし（v1） Claude Opus 4.7 サブスク枠（追加 0 円） メイン運用

なぜ Claude Agent SDK 版がメインか

  • 固定費: 月額 $20 (Pro) または $100 (Max 5x) で予算予測可
  • API 課金回避: 1本あたり $0.5〜1 相当が、サブスクの月額に含まれる
  • 品質: Opus 4.7 を使えるため、Anthropic API 版と同等出力
  • レート制限内: Pro でも 5h あたり ~190 本生成可能
共通プロンプト設計

場所: .claude/manual-prompt-card.md

同ファイルには2つのコードブロックがあり、1つ目が SYSTEM_PROMPT、2つ目が USER_PROMPT_TEMPLATE。

プロンプトに記述している要件（要約）

  • SeeFT デザインシステムのカラー（teal #009688、ゴールド枠線 #C9A227 等）
  • 目次セクション + 章ごとの折りたたみ + ライトボックス + フローティング目次ボタン
  • カンバン形式の役割分担カード（1枚で完結する情報密度）
  • TOC ボタンカード、章末ナビ、サブ目次（pillナビ）
  • スマホ縦持ち最適化、本文 15px 以上、補助 12px 以上
  • 元 Markdown にない情報を絶対に追加しない（メタ説明文・略称・UI ヒント等を禁止）
  • 元 Markdown のコンテンツを絶対に省略しない

プロンプト更新時の注意

プロンプトの構造を壊さないこと

  • コードブロック数 (` ``` ` で区切られたブロック) は必ず2つ。1つ目=SYSTEM、2つ目=USER。スクリプトの _load_prompt_from_md() はこれを位置で判定する
  • 3つ目以降のコードブロックを書く場合、別ファイルか、コードブロック外（テキスト）に書く
  • USER_PROMPT_TEMPLATE は {image_list} と {html_content} プレースホルダーが必須
運用コマンド

単一マニュアル生成（メイン: Claude Agent SDK）

uv run --project scripts/claude-slide python scripts/claude-slide/generate_slide.py --prompt card --model claude-opus-4-7 docs/manuals/01_44th_配線マニュアル

全マニュアル一括生成

for d in docs/manuals/*/; do name=$(basename "$d"); echo "===== $name ====="; uv run --project scripts/claude-slide python scripts/claude-slide/generate_slide.py --prompt card --model claude-opus-4-7 "$d" || echo "FAIL: $name"; done

8マニュアル合計 30-40 分、サブスク 8 メッセージ消費（Pro の 5h 枠の 18% 程度）。

Sakura 版（フォールバック）

export SAKURA_API_KEY=... uv run --project scripts/sakura-slide python scripts/sakura-slide/generate_slide.py --prompt card docs/manuals/01_44th_配線マニュアル

Anthropic API 版（保険）

export ANTHROPIC_API_KEY=sk-ant-... python3 scripts/generate_manual_slide.py --prompt card docs/manuals/01_44th_配線マニュアル

出力の確認

ls -lh docs/manuals/*/slide_claude.card.html
既知の挙動・対処

max_turns=10 の安全マージン

Claude Agent SDK 版は max_turns=10 に設定済。

背景

大入力（28KB+ markdown）で Claude が稀に内部的にツール試行する挙動があり、max_turns=1 だと「Reached maximum number of turns (1)」エラーで失敗するケースがあった。max_turns=10 で安全マージンを確保。実際の num_turns は 1 で済むことが多い。

エラー表示が紛らわしい問題

SDK のエラーメッセージ "Claude Code returned an error result: success" は誤解を生む表示。実体は内部 turn 上限超過などの別エラー。max_turns 拡大で回避できる。

画像配置の精度

LLM はファイル名と figcaption の順序から推測して画像を配置する。

  • Opus 4.7 はこの推論が強く、配線マニュアル 25 枚で全配置成功
  • ファイル名が完全に非記述的（image1.png 等）でも、figcaption が明確なら正確に配置される
  • 失敗するなら原因は元 Markdown の図キャプションが曖昧
  • vision 化（画像も LLM に渡す版）の検討は manual-slide-vision-todo.md 参照

プロンプト遵守のクセ

LLM が犯しがちなルール違反（プロンプトで明示的に禁止済）

  • 「カードだけ見れば動ける構成」のような UI 設計の自己言及をマニュアル本文に書く
  • 「タップで発信」のような UI ヒントを書く
  • 「BTタップ」のように勝手に略称を作る
  • 章タイトルから自明な lead 文を追加する
  • 元 Markdown の「該当シフト」のような短い節を省略する

生成物を見て上記が混入していたら、プロンプトの「厳守事項」セクションを強化して再生成する。

トラブルシューティング

「Reached maximum number of turns」エラー

  • 原因: 大きい入力で Claude が tool 試行 → max_turns 超過
  • 対処: scripts/claude-slide/generate_slide.py の max_turns 値を増やす（既定 10、最大 20 程度まで増やしても OK）

サブスクのレート制限に当たった

  • 原因: 短時間に多数の生成 → Pro の 5h あたり ~190 本制限突破
  • 対処1: 5h 経過後に再実行
  • 対処2: Max プランへ一時的にアップグレード
  • 対処3: 失敗したマニュアルだけ Sakura または Anthropic API 版で生成

画像配置が崩れる

  • 原因1: 元 Markdown の figcaption が曖昧
  • 対処1: Google Doc 側の図キャプションを明確にして再生成
  • 原因2: 画像ファイル名と内容のミスマッチ
  • 対処2: vision 化の検討（manual-slide-vision-todo.md 参照）

pandoc がない / インストールできない

  • Homebrew で brew install pandoc
  • Linux なら apt install pandoc

サブスクの認証が切れた

  • claude login を実行して再認証
  • サブスクが切れている場合は契約更新、または別バックエンド（Sakura / API 鍵）に切り替え
残課題と進化方針（v2 候補）

v1 として 8マニュアル安定生成までは到達済。以下は新 PM の判断で実装するかどうか決める候補。

vision 化

優先度: 中
  • LLM に画像も渡して配置精度向上
  • コスト +27% ($0.97 → $1.19/本)
  • Pro でも 5h あたり 190 本維持可
  • 判断軸: 配置失敗が実運用で出てから着手
  • 詳細: manual-slide-vision-todo.md

自己レビューループ

優先度: 中
  • 生成 → プロンプト準拠チェック → 修正の自動化
  • Claude Agent SDK の max_turns を拡張して実装可能
  • 品質の下振れを抑える
  • サブスク消費は増える（チェック分の1メッセージ追加）

compare スクリプト3バックエンド化

優先度: 低
  • 現状 scripts/compare_manual_versions.sh は Sakura 専用
  • --backend オプションで切替できるよう拡張
  • 品質比較が必要なフェーズで着手

中間 Markdown の永続化

優先度: 低
  • pandoc 変換結果がメモリ上のみなのでデバッグ時に再現できない
  • --save-md フラグで preview.md 出力できるように
  • 配線マニュアルだけ手動で残してある

カスタムフォント・テーマ

優先度: 低
  • 現状は system-ui + teal/gold
  • SeeFT 公式デザインシステムが固まったら反映
  • プロンプトの「カラースキーム」セクションだけ更新
