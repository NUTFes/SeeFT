## Q1. 45thマニュアル作成者は何をすればよいか

> 「45thマニュアル作成者は例年と同じようにスライド作っていただければ良いです！ドキュメントってこと？」

そのとおり。**マニュアル作成者は普段どおり Google Document を書くだけ**。追加作業はゼロ。

ただし、AI が正しく変換できるよう、以下の「既存ルールを継続」してもらえると精度が上がる（特別なテンプレートではなく、「普通に整って書く」だけ）:

| 項目 | やってほしいこと |
| --- | --- |
| 見出し階層 | H1 / H2 / H3 を意味的に使う（例: `# 該当シフト` / `## 集合場所`） |
| 画像 | キャプションを必ずつける（例: 「図 講義棟前案内所配置図」）。AI は本文と画像キャプションから配置を判断する |
| 連絡先 | 電話番号は普通のテキストで書く（例: `090-XXXX-XXXX`）→ 生成 HTML で自動的にタップ発信化される |
| テーブル | Google Docs のテーブル機能で作る → 自動で HTML テーブルに変換される |
| 固有名詞 | 略称を使わない（例: 「BTタップ」→「ブレーカータップ」と正式名で書く）。AI は元 Doc の表記をそのまま尊重する |
| 完成後 | SeeFT 運用フォルダに保存（場所は別途指定） |

**やらなくていいこと**: 特別なテンプレ準拠 / HTML を書く / スマホレイアウトの考慮 / メタデータ追加 — どれも不要。

## Q2. どのような工程でスライドを作るのか

> 「大体のフローとしては、マニュアル作成担当者が作成→指定フォルダに移動→Seeftがhtmlエクスポート→スライドが完成しマニュアル確認担当者がドキュメントと内容照合→以降、マニュアルに変更が生じ次第繰り返す」

ほぼ正解。補足するとこうなる:

```
[マニュアル作成者]
   ↓ Google Doc 編集
   ↓ 完了 or 更新したら PM に通知

[PM（上林、引き継ぎ後は新PM）]
   ↓ Doc を HTML エクスポート（Google Docs の「ダウンロード → Web ページ」）
   ↓ ローカルで生成ツール実行（コマンド1回、3〜6 分）
   ↓ 生成された Web ページを SeeFT の配信先にデプロイ
   ↓ SeeFT シフトページのリンクを更新（Doc URL → Web ページ URL）

[マニュアル確認担当者]
   ↓ 元 Doc と生成 Web ページを照合
   ↓ OK → 完了 / NG → PM に修正依頼

[技大祭当日も同じフロー: Doc 変更 → PM 再生成 → URL は同じまま中身だけ更新]
```

検証は「元 Doc と生成物が同じ内容か」だけで OK。外部知識（教科書等）で正しさを調べる必要はない。

## Q3. 内容の誤りの訂正方法

エラーの原因によって対応者が分かれるので、3 パターンで整理:

| 原因 | 例 | 対応者 | 対応方法 |
| --- | --- | --- | --- |
| A) AI の出力ミス | 章の順序が変、画像配置ずれ、勝手に追加した一文がある | PM | 再生成を試す（多くは flaky で直る）。直らない場合はプロンプト調整して再生成 |
| B) 元 Doc に誤り | 連絡先の電話番号が違う、必要物品の数が違う | マニュアル作成者 | Google Doc を修正 → PM に再生成を依頼 |
| C) レイアウト崩れ | テーブルが横にはみ出す、画像が小さすぎる | PM | プロンプトの該当部分を調整 → 該当マニュアル（必要なら全部）を一括再生成 |

**重要な性質**: AI は「元 Doc にないことは書かない」設計（プロンプトで厳禁化済）。だから「AI が嘘の連絡先を発明した」みたいな致命的な誤りは構造的に起きにくい。誤りはほぼ「A) AI ミス」か「B) Doc ミス」のどちらかに収まる。

## Q4. マニュアル変更時の対応フロー

> 「マニュアル変更の際の対応も決めなきゃだね」

具体的に明文化すると:

1. マニュアル作成者: Google Doc を編集（追記・修正）
2. マニュアル作成者: 完了したら PM に Slack 等で通知
3. PM: 再エクスポート + 再生成（3-6 分）
4. PM: 生成 Web ページを配信先に再アップロード（SeeFT シフトページの URL は同じまま、中身だけ更新）
5. 確認担当者: 改めて元 Doc との整合を確認 → OK で完了

**当日も同じ運用が可能**: マニュアル更新 → PM 連絡 → 5-10 分で反映 → 各担当者の手元は自動で最新版に切り替わる（リンクは変わらないため）。

### 執行部 MT で詰めたい事項

- マニュアル作成者から PM への通知チャネル（Slack のどのチャンネル / DM か）
- 更新頻度の上限（当日中の更新は何回まで OK か）
- PM 不在時のバックアップ運用（緊急時に再生成できる人がもう 1 人いた方が安全）
- **自動化フローの設計**（→ 後述「やること（TODO）: 自動化フローの確立」参照）
- **新 PM の Mac セットアップ日程**（→ 後述「やること（TODO）: ベトナム期間中の運用体制」参照）

## Q5. その他注意点

| ポイント | 内容 |
| --- | --- |
| 画像のキャプションが命 | AI は画像を直接見ない（現バージョン）。キャプションから内容を推測して配置するので、具体的に書いてもらえるほど精度が上がる |
| AI に補完を期待しない | 「ここは AI が空欄を埋めてくれる」と思って書かない。元 Doc にないことは AI も書かない設計（これが安全性の根幹） |
| コスト | 月額 $20（約 3,000 円）のサブスクのみ。マニュアル本数が増えても追加課金なし |
| 生成スループット | 5 時間に約 190 本まで生成可能。技大祭規模では余裕（実マニュアル100本程度） |
| フォールバック | 仮にメイン AI サービスが落ちても、別バックエンド（Sakura AI Engine / Anthropic API）で代替可能（PM 内部の運用知識） |

## Q6. なぜこのパイプラインは「安全」と言えるのか（背景説明）

このパイプラインは、AI 用語で言う「情報圧縮タスク」に分類される。AI が新しい情報を作っているのではなく、既存の Google Doc を「スマホで読みやすい形に組み替えている」だけ。

この性質から得られる安全性:

- **検証が安い**: 元 Doc を見れば正しさが確認できる。外部知識（教科書・専門家）は不要
- **ハルシネーション耐性**: AI の出力確率分布が入力 Doc に強く制約されるので、「もっともらしい嘘」が混入しにくい
- **モデル差が出にくい**: 入力が出力を強く制約するので、安いプランの AI でも一定の品質が出る
- **本数スケールに耐える**: 本数が増えても検証コストはほぼ線形（1 本あたり数分の目視チェック）

### 禁止区域（このパイプラインで「やらないこと」）

逆に以下のような使い方をすると「情報拡張タスク」になり、安全性が崩れる:

- Doc にない補足説明を AI に書かせる
- Doc が不完全な所を AI に「いい感じに」補完させる
- 複数 Doc を横断して新規マニュアルを生成

これらは禁止区域として運用ルール化する。マニュアルパイプラインは「圧縮専用」、新規マニュアル制作は人間が Doc で書く、という役割分担が前提。

## やること（TODO）: 自動化フローの確立

現状、PM が手動で行う工程が多い。これを Google Spreadsheet を起点にした自動化フローに置き換えることを検討中。**この設計を執行部 MT で議論 + 詰めたい**。

### 現状の手動工程（PM が毎回やる）

1. マニュアル作成者から「更新しました」連絡を受ける
2. Google Docs を開いて HTML エクスポート
3. ローカルの該当フォルダに展開
4. ツール実行コマンドを叩く
5. 生成された Web ページを配信先にアップロード
6. SeeFT シフトページのリンク URL を更新
7. 確認担当者に「確認お願いします」と通知

→ **1マニュアルあたり 5-10 分の PM 作業**。10 本更新があれば 1-2 時間。技大祭直前の駆け込み更新でボトルネックになる懸念。

### 目指す姿（自動化後）

マニュアル作成者が Google Doc を更新するだけで、SeeFT 側のリンク先 HTML が自動で最新になる。PM の介入は例外時のみ。

### 検討する設計案

#### 案 A: スプシ起点（PM がスプシを更新 → 自動生成）

スプレッドシートで全マニュアルを管理:

| マニュアル名 | Google Doc URL | 担当者 | 生成済 HTML URL | 最終生成日時 | ステータス |
| --- | --- | --- | --- | --- | --- |
| 配線マニュアル | https://docs.google.com/.../edit | 田中 | https://.../slide.html | 2026-05-12 13:30 | OK |
| 案内所準備・片付け | ... | 赤嶺 | ... | ... | 要確認 |

- PM が「ステータス」列を「再生成」に変える → Apps Script or 外部スクリプトが検知 → 生成 → ステータス「OK」に更新
- 利点: スプシで全状況が見える、再生成タイミングを PM が制御、引き継ぎがスプシ閲覧で完結
- 課題: スクリプト実装と保守、Doc → ローカル → 生成 → デプロイの橋渡し方法、認証

#### 案 B: Drive Trigger 起点（Doc 編集を自動検知 → 自動生成）

- Google Drive API の Push Notification で Doc 編集を検知 → 自動再生成
- 利点: マニュアル作成者の通知不要、常に最新
- 課題: 編集中に何度も走る（防止策が必要）、Drive API レート制限、頻繁な編集で計算リソース無駄

#### 案 C: GitHub Actions 起点（Doc URL をリポジトリに登録）

- リポジトリ内に Doc URL リストを持つ
- GitHub Actions の定期実行（例: 毎日深夜）で一括再生成
- 利点: 既存リポジトリ運用と統合、ログが残る、CI/CD の枠組みで扱える
- 課題: 定期実行なので即時性なし、Actions の制限内に収める必要、サブスク認証をどう持たせるか

#### 案 D: ハイブリッド（手動 + スプシで状態管理）

- 生成は PM の手動コマンド（今と同じ）
- ただしマニュアル一覧・状態管理はスプシで一元化
- PM がスプシを見て次に再生成すべきものを判断
- 利点: 実装が軽い、まず「見える化」だけ進める、Phase 1 として最速で着手可能
- 課題: 自動化の効果は限定的（PM 作業が省ける部分は少ない）

### 決めなきゃいけない事項

- [ ] 案 A / B / C / D のどれを採用するか（または組み合わせ）
- [ ] スプシのカラム定義（最低限のフィールド）
- [ ] スプシのオーナー（誰が編集権限を持つか、共有範囲）
- [ ] 生成 Web ページのホスティング先（GitHub Pages / Drive 公開 / SeeFT 内部静的 / その他）
- [ ] SeeFT シフトページの URL 更新方法（手動 / API / スプシ連携）
- [ ] 生成失敗時の通知方法（Slack DM / メール / スプシのステータス列）
- [ ] PM 不在時のバックアップ運用（自動化で代替できる範囲）
- [ ] 認証の持ち方（PM 個人サブスク → スクリプトに OAuth トークン埋め込み？）

### 段階的な進め方（提案）

**Phase 1（今週〜来週）: 状態管理だけスプシ化**

- 案 D の軽量版
- スプシを作って全マニュアルを一覧化（マニュアル名 / Doc URL / 担当者 / ステータス / 最終生成日時）
- PM は今と同じ手動操作だが、スプシで状況管理
- 実装コスト最小（スプシ作るだけ）
- これだけでも「どこまで生成済か」「どこが古いか」が見えるので運用が楽になる

**Phase 2（5月後半〜6月）: 半自動化**

- 案 A の実装
- スプシのステータス変更 → スクリプト（Google Apps Script or ローカル監視）→ 再生成 → デプロイ
- PM はスプシのセルを変えるだけで再生成できる
- 実装コスト中（スクリプト + デプロイ自動化）

**Phase 3（引き継ぎ後〜技大祭前）: 完全自動化（任意）**

- 案 B（Drive Trigger）の検討
- 効果（即時更新）と実装コスト（webhook 構築、レート制御）を比較して採用判断
- 新 PM が運用してみて必要性を感じたら着手

### このセクションの位置付け

執行部 MT では「**Phase 1 をいつ・誰がやるか**」までは決めたい。Phase 2 以降は引き継ぎ後の新 PM とも相談して進める。

このタスクは別途 issue / branch を切って進める想定。完了したら本 Q&A md にも反映する。

## やること（TODO）: AI 自動検証の組み込み

生成された HTML が元 Doc と整合してるかを **生成 AI 自身に検証させる** フロー。ハルシネーション検出を人間任せにせず、AI 検証 + 人間最終確認の 2 段構えにする。

### 理論的根拠（執行部に聞かれたら）

検証タスクは入力 (元 Doc + 生成 HTML) が両方 AI の手元にあって、新事実を作らない = **情報圧縮タスク**。生成と同じく、ハルシネーションリスクが構造的に低い。**「ハルシネーション検出すらハルシネーションせずできる」** 安全な使い方。

### 検証 Phase の段階分け

#### 検証 Phase 1: AI 単体（最初に実装、約 1 時間）

- 入力: 元 Doc (Markdown) + 生成 HTML
- 出力: 「OK」or「元 Doc にない情報リスト + 元 Doc にあるのに欠落した情報リスト」
- 実装: `scripts/claude-slide/verify_slide.py` を新規作成（既存 generate_slide.py のパターンに乗せる）

#### 検証 Phase 2: コード薄レイヤーを前置（オプション、1-2 時間）

- AI 検証の前に、電話番号・物品数・画像ファイル名等の厳密照合をコードで実施
- 致命的不一致は AI を呼ばずに早期検出 → コスト節約

#### 検証 Phase 3: 構造化出力で完全自動化（半日）

- AI に JSON 形式で問題を返させて、スプシ + GAS が結果を自動パース
- ステータス遷移を完全自動化

### 検出できる / できないこと

| 検出できる | 検出できない |
| --- | --- |
| HTML 中の数字・固有名詞の改変 | 画像の中身（vision 未対応のため） |
| 元 Doc にないメタコメント・略称 | 元 Doc 自体の事実誤り |
| 章構造の欠落・順序入れ替え | レイアウトの美しさ |
| 連絡先電話番号の改変 | スマホ表示の崩れ |

## やること（TODO）: ベトナム期間中の運用体制

上林（PM）が 2026-09月からベトナム滞在となるため、技大祭本番期間は**新 PM が完全に独立して運用できる状態**を 8 月引き継ぎ完了時点で達成する必要がある。

### 確定した方針

**メインバックエンド: 上林の Claude Max プランを新 PM と共用**

- 上林の既存 Max プラン契約の容量を新 PM が利用する
- 追加コストゼロ（既に上林が支払い中）
- 新 PM の Mac に 1 度だけ `claude login` → OAuth トークンが保存される → 以降は新 PM が普通にコマンドを叩くだけ
- ベトナム滞在中の上林はほぼ Claude を使わない → 実質単一ユーザーパターンになり、TOS リスクは実用上ほぼゼロ
- ベトナム終了後（10月以降）に方針を再決定（新 PM 個人契約に移行 or 共用継続）

**保険バックエンド: Anthropic API キー**

- SeeFT 組織で API キーを取得しておく（使わなければ課金ゼロ）
- Max アカウントが想定外にロックされた / 認証エラーが出た場合のみ起動
- 既存スクリプト `scripts/generate_manual_slide.py` で代替（生成 30 本程度なら $30 前後で吸収可能）

**Sakura AI Engine: 採用しない**

- gpt-oss-120b の品質落差が大きい（過去検証済）
- 緊急時でも品質を落とすメリットなし

### TOS リスクを最小化する運用ルール

| ルール | 理由 |
| --- | --- |
| 1 Mac = 1 アカウント運用 | 同時に複数 Mac で同じアカウントを使わない |
| ベトナム期間中は上林の他デバイスでログアウトしておく | 並行アクセスをゼロに |

### 検討して却下した選択肢

**新 PM が個人で Pro 契約 → 経費精算**

- 月額 $20 を SeeFT 予算から立替する手続きが必要
- 上林の Max 容量が大幅に余っているのに別契約するのは無駄
- 学生 PM のクレカ登録ハードルもあり

**完全クラウド化（GitHub Actions + API キー、サブスクなし）**

- 工数 2-3 日かかる
- 既存サブスクで間に合うので投資効果が低い
- 新 PM の Mac で毎日起動できる前提なら不要

### 緊急時のフォールバック

新 PM の Mac が起動できない / Max アカウントがロックされた / その他の障害が起きた場合:

1. まず API キー（保険）で `scripts/generate_manual_slide.py` を起動
2. それも動かない場合は、執行部メンバー誰でも手動コマンドが叩ければ生成可能
3. 最後の手段: 当該マニュアルだけ Google Doc リンク経由で運用継続（旧方式）

**「手動コマンドが叩ければ動く」状態を常に維持**しておくことで、最終フォールバックを確保。
