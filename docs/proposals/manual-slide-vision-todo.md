# 解説マニュアル生成パイプラインに vision を入れるか検討

ステータス: 未決定（議論記録）
最終更新: 2026-05-11
関連ファイル:
- `scripts/claude-slide/generate_slide.py` (Claude Agent SDK 版、現状テキスト推論のみ)
- `scripts/sakura-slide/generate_slide.py` (Sakura 版、vision 未対応モデルなので不可)
- `scripts/generate_manual_slide.py` (Anthropic API 版、既に vision 実装済)
- `.claude/manual-prompt-card.md` (共有プロンプト)

## 背景

現状 Claude Agent SDK 版は、Anthropic API 版に比べて**画像を LLM に渡していない**。
画像はファイル名のリストだけ user prompt に入れて、配置は LLM の Markdown 文脈推論に任せる Sakura と同じ方式を採用している。

採用の理由:
- `query()` の prompt パラメータが string で、multimodal content blocks を直接渡せない
- 画像送信実装に SDK 側の追加調査が必要
- このセッションで Opus 4.7 が「ファイル名だけ + figcaption の順序」から正しく配置できることを実証済み（配線マニュアル25枚、全配置成功）

しかし、よりロバストにするなら vision を入れる選択肢がある。それを評価する。

## コスト試算（配線マニュアル / 25枚で実測）

トークン換算は Anthropic 公式の `tokens ≈ (width × height) / 750` 公式と、画像ごとの上限 1568 tokens（auto-resize）を使用。

実画像から計算した結果:
- 25枚合計: **17,001 image tokens**
- 平均: **680 tokens/枚**
- 上限ヒット: 1枚（image3.jpg, 2MP の大判写真のみ）
- ディスクサイズ合計 3478KB

これを現状ランと比較すると以下になる。

| 項目 | 現状（テキストのみ） | + 画像送信 |
| --- | --- | --- |
| 入力 text tokens | 約 20,000 | 約 20,000 |
| 入力 image tokens | 0 | 約 17,000 |
| 出力 tokens | 約 8,500 | 約 8,500（変化なし） |
| **入力合計** | 20K | **37K (+85%)** |
| **API 換算コスト** | $0.97 | **$1.19 (+$0.25, +27%)** |

実ランの $0.97 と試算の $0.94 がほぼ一致するので、+$0.25 の試算は信頼できる。

サブスク認証で動かす場合この $1.19 は実支払額ではなく**API 換算メトリクス**で、月額サブスクから追加課金は発生しない。ただしレート制限のトークンカウンタは消費する。

## サブスクのレート制限への影響

5時間あたりの入力トークン上限ベース:

| プラン | 月額 | テキストのみ運用 | 画像付き運用 |
| --- | --- | --- | --- |
| Pro | $20 | 約 350本/5h | 約 190本/5h |
| Max 5x | $100 | 約 1,750本/5h | 約 950本/5h |
| Max 20x | $200 | 約 7,000本/5h | 約 3,800本/5h |

画像を入れると throughput が約半減するが、**Pro プランでも 5時間に 190本生成可能**。SeeFT のマニュアル本数（数十本規模）なら Pro で十分余裕。

## 質的改善の見込み

vision を入れる効果が出やすいケース:
- ファイル名が `image1.png` のように非記述的（今回がこれ）
- Markdown の figcaption が曖昧または欠落
- 似たような図が複数あって順序判別が必要
- 画像の中身に応じてレイアウト調整したい（横長は full-width など）

vision の効果が小さいケース:
- 元 figcaption が完璧に対応している（テキスト推論で足りる）
- 写真が「ある/ない」のフラグでよい
- 画像が装飾的で意味論的配置が問われない

**配線マニュアルのケース**: 「ファイル名は非記述的だが figcaption は完璧」の中間ケース。Opus 4.7 はテキスト推論で正確に配置できた。Sonnet/Haiku 等の低性能モデルだと vision を入れる効果は相対的に大きくなる。

別マニュアル（案内所準備・片付け、お化け屋敷など）でも検証してから判断するのが望ましい。

## 実装の選択肢

### 案 A: ClaudeSDKClient + custom content blocks

`query()` ではなく `ClaudeSDKClient` の interactive API を使い、メッセージに image content block を含める。

良い点:
- 公式のマルチモーダル送信機構を使える
- max_turns=1 のまま単発生成セマンティクスを維持できる

要調査:
- `ClaudeSDKClient` が image content block を受け付けるか公式ドキュメントで未確認
- メッセージフォーマットの詳細

### 案 B: Read tool 解禁

`allowed_tools=["Read"]` を許可し、Claude にプロンプト内で「このディレクトリの画像を Read tool で確認してから配置してください」と指示する。

良い点:
- 実装が単純（オプション 2 行変更）
- 既存の Claude Code エコシステムをそのまま活用

注意点:
- 各 Read 呼び出しが 1 turn 消費。25 枚読むと max_turns 30+ 必要
- サブスクのメッセージカウンタを早く消費する（messages/5h リミット）
- LLM が「全部読まずに済ます」と判断して飛ばす可能性
- agentic 挙動になり出力の決定性が落ちる

### 案 C: 現状維持

text-only で続ける。

良い点:
- コスト最小
- 既に動いている

悪い点:
- ファイル名が非記述的なドキュメントで配置精度が落ちるリスク
- 弱いモデル（Sonnet 4.6 など）に切り替えた時の品質低下耐性が低い

## 判断のための質問

以下を試してから決める:

1. 別マニュアル（案内所準備・片付け、お化け屋敷）で text-only の Claude Agent SDK 版を実行し、配置精度を確認する
2. もし配置の崩れが出るマニュアルがあれば、それを vision 化のテストケースにする
3. 配置精度の改善が顕著で、サブスクのレート制限に余裕があれば案 A を実装する

## 関連する設計上の発見

- 既存の Anthropic API 版 (`scripts/generate_manual_slide.py`) は「500KB 超画像をスキップ + 最大20枚」というガードを実装している。これは古い API 制限の名残。Anthropic auto-resize がある現在、500KB スキップは外せる（20枚キャップは念のため残す）
- 1枚あたり約 700 tokens、約 $0.01-0.015 の鉛筆計算が使える
- 出力 tokens は vision 有無で変わらない（生成 HTML サイズが同じだから）。コスト増は完全に入力側に閉じる
