# 0006: Close #N を書くときは、番号の issue の中身と照らし合わせる

- 状態：採用
- 決めた日：2026-06-21
- 決めた人：45th の PM
- 出典：#352、#308、#309

## 背景

mobile の lint の違反をまとめて直した PR（#352）の本文に、`Close #303` から `Close #309` までを並べた。ところが #308 と #309 は、この PR では直していない別の違反の issue だった。ブランチ名の番号の並びに引きずられて取り違えたもので、マージすると2件とも閉じてしまい、同じ日に開き直した。

`Close #N` や `resolve #N` は、issue の中身を見ずに、番号だけで issue を閉じる。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 気をつけて書く | 手間がない | 今回も気をつけていたつもりで取り違えた |
| close のキーワードを使わず、マージ後に手で閉じる | 誤って閉じることはない | 閉じ忘れが出る。PR と issue の結び付きが残りにくい |
| キーワードは使い、PR を出す前に各番号の題名を確かめる | 自動で閉じる便利さを残したまま、取り違えを防げる | 確かめる手間がかかる |

## 決定

`Close #N`・`resolve #N` を書くときは、PR を出す前に `gh issue view <N> --json title` で各番号の題名を確かめ、直した内容と1対1で照らし合わせる。マージした後も、閉じた issue が意図どおりかを確かめる。

## 理由

close のキーワードは便利だが、誤りに気づくのはマージした後になる。題名を1回確かめるだけで取り違えは防げるので、キーワードをやめるより、確かめる手順を足す方が得だった。

## 前提

- GitHub の close キーワードの仕組み（中身に関係なく番号で閉じる）
- 決まりの本体は `docs/development/workflow.md` の5節
