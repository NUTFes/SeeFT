# 0002: 文書の変更も issue → ブランチ → PR を通す

- 状態：採用
- 決めた日：2026-05-01
- 決めた人：45th の PM
- 出典：コミット `2f7b8bb`（`AGENTS.md` の Git Workflow に明記）

## 背景

`AGENTS.md` を作るときに、文書の変更までいちいち issue と PR を通すかを決める必要があった。文書は動作に影響しないので、develop に直接コミットしても壊れるものはない。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 文書は develop に直接コミットしてよいことにする | 手間が少ない | なぜ変えたかが履歴に残らない。レビューを通らない |
| コードと同じく issue → ブランチ → PR を通す | 目的が issue に、議論と確認が PR に残る。CodeRabbit のレビューが効く | 小さな変更でも手間がかかる |

## 決定

`AGENTS.md`・README・設定ファイルなどの文書の変更も、issue を立て、ブランチを切り、PR を出す。「軽い変更だから」を理由に工程を省かない。

## 理由

工程を省くと、後から入った人が履歴をたどっても、なぜその文書がそうなっているのかが分からない。とくに `AGENTS.md` は規約そのものなので、変えた理由が残らないと、規約を変えてよいのかを後から判断できない。

また、`AGENTS.md` は CodeRabbit のレビューの対象にもなる。PR を通せば、文書の食い違いや誤りを機械に拾わせられる。

## 前提

- 決まりの本体は `AGENTS.md` の Git Workflow と `docs/development/workflow.md`
- develop に、PR を通さないとマージできない保護ルールが掛かっている

## 結果

45th の後半の文書の変更（`docs/operations/` を足した #554〜#562、ADR を入れた #568 など）は、すべて issue と PR を通した。PR の本文に目的と確かめたことが残り、CodeRabbit が文書の食い違いを指摘した例もある（#568 の README と `AGENTS.md` の決まりの食い違い）。
