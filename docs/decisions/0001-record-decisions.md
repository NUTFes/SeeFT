# 0001: 判断の理由をADRとしてリポジトリに残す

- 状態：採用
- 決めた日：2026-09-30
- 決めた人：45thのPM
- 出典：#567

## 背景

45thから46thへの引き継ぎの準備で、45thのPMが過去のMTの資料を読み直した。資料には過程と結果しか書かれておらず、なぜそうしたかが分からなかった。

理由が残らない原因は3つあった。

- 方針の議論をSlackでしていた。Slackは無料プランのため、90日を過ぎると読めなくなる
- PRとissueには採った案だけが残り、比べた候補や見送った理由が残らない
- 判断の基準（何をissueにするか、何を公開しないか、など）が、PM個人や、PMが使っていたAIのコーディング支援ツールの記憶の中にしかなかった

後任が「この作りは変えてよいのか」「前にこの案を見送ったのはなぜか」を自分で判断するには、理由と候補が読める形で残っている必要がある。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 何もしない（MTの資料に理由も書くよう心がける） | 手間が増えない | これまでも心がけでは残らなかった |
| Notionにまとめる | MTの資料と同じ場所に置ける。非公開の内容も書ける | 読むのにワークスペースへの招待が要る。コードとは別の場所にあり、コードが変わっても気づけない |
| GitHubのWikiにまとめる | リポジトリと同じ場所から読める | PRを通らないのでレビューされない。コードと同じ履歴で管理されない |
| リポジトリの`docs/decisions/`にADRを置く | PRでレビューされる。コードと同じ履歴で管理される。前提にしたコードが消えたらCIで気づける。誰でも読める | 公開リポジトリなので、個人名や未公開のセキュリティの問題は書けない |

## 決定

判断の理由を、ADRとしてリポジトリの`docs/decisions/`に残す。前提に書いたファイルと関数がまだ存在するかを、PRごとにCIで確かめる。

## 理由

理由を読みたくなるのは、たいていコードを変えようとしたときである。そのときに開くリポジトリの中にあり、コードと同じPRの流れでレビューされる場所がいちばん残りやすい。前提にしたコードが消えたときにCIが落ちれば、古くなった判断を読み続けてしまうことも防げる。

公開リポジトリに書けないもの（個人名、ID、未公開のセキュリティの問題）は、これまでどおり非公開の資料とGitHubの非公開のセキュリティアドバイザリで扱う。ADRにはそちらへの参照だけを書く。

## 前提

- 書き方の決まりは`docs/decisions/README.md`、雛形は`docs/decisions/template.md`
- 点検は`scripts/refcheck/refcheck.py#check_span`が行い、`.github/workflows/docs-refcheck.yml`がPRごとに走らせる
- ADRを書くルールは`AGENTS.md`にもある。AIのコーディング支援ツールも同じルールでADRを書く

## 追記

- 2026-09-30：ADRにするものを、システムの作りや本番の運用に関わり、後から戻すのに手間がかかる判断に絞った。PRの書き方やタスクの割り振り方などのチームの約束事は、ADRにせず`docs/development/workflow.md`に理由と一緒に書く。あわせて、決める前に「提案」で書く流れと、確信度の欄を足した（#569）
