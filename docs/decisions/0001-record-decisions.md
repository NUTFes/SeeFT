# 0001: 判断の理由を ADR としてリポジトリに残す

- 状態：採用
- 決めた日：2026-09-30
- 決めた人：45th の PM
- 出典：#567

## 背景

45th から 46th への引き継ぎの準備で、45th の PM が過去の MT の資料を読み直したところ、過程と結果しか書かれておらず、なぜそうしたかが分からなかった。

理由が残らない原因は3つあった。

- 方針の議論を Slack でしていた。Slack は無料プランのため、90日を過ぎると読めなくなる
- PR と issue には採った案だけが残り、比べた候補や見送った理由が残らない
- 判断の基準（何を issue にするか、何を公開しないか、など）が、PM 個人や、PM が使っていた AI のコーディング支援ツールの記憶の中にしかなかった

後任が「この作りは変えてよいのか」「前にこの案を見送ったのはなぜか」を自分で判断するには、理由と候補が読める形で残っている必要がある。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 何もしない（MT の資料に理由も書くよう心がける） | 手間が増えない | これまでも心がけでは残らなかった |
| Notion にまとめる | MT の資料と同じ場所に置ける。非公開の内容も書ける | 読むのにワークスペースへの招待が要る。コードとは別の場所にあり、コードが変わっても気づけない |
| GitHub の Wiki にまとめる | リポジトリと同じ場所から読める | PR を通らないのでレビューされない。コードと同じ履歴に乗らない |
| リポジトリの `docs/decisions/` に ADR を置く | PR でレビューされる。コードと同じ履歴に乗る。前提にしたコードが消えたら CI で気づける。誰でも読める | 公開リポジトリなので、個人名や未公開のセキュリティの問題は書けない |

## 決定

判断の理由を、ADR としてリポジトリの `docs/decisions/` に残す。前提に書いたファイルと関数がまだ存在するかを、PR ごとに CI で確かめる。

## 理由

理由を読みたくなるのは、たいていコードを変えようとしたときである。そのときに開くリポジトリの中にあり、コードと同じ PR の流れでレビューされる場所がいちばん残りやすい。前提にしたコードが消えたときに CI が落ちれば、古くなった判断を読み続けてしまうことも防げる。

公開リポジトリに書けないもの（個人名、ID、未公開のセキュリティの問題）は、これまでどおり非公開の資料と GitHub の非公開のセキュリティアドバイザリで扱う。ADR にはそちらへの参照だけを書く。

## 前提

- 書き方の決まりは `docs/decisions/README.md`、雛形は `docs/decisions/template.md`
- 点検は `scripts/refcheck/refcheck.py#check_span` が行い、`.github/workflows/docs-refcheck.yml` が PR ごとに走らせる
- ADR を書くルールは `AGENTS.md` にもある。AI のコーディング支援ツールも同じルールで ADR を書く

## 追記

- 2026-09-30：ADR にするものを、システムの作りや本番の運用に関わり、後から戻すのに手間がかかる判断に絞った。PR の書き方やタスクの割り振り方などのチームの約束事は、ADR にせず `docs/development/workflow.md` に理由と一緒に書く。あわせて、決める前に「提案」で書く流れと、確信度の欄を足した（#569）
- 2026-09-30：「確信度」の欄を「決定の信頼度」に改め、なぜその信頼度かの根拠を書く行を足した。0002〜0006 にも根拠を足した（#590）
