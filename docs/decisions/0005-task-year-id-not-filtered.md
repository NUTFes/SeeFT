# 0005: tasksのseed由来の行は年度をまたいで使い、名前で引くときにyear_idで絞らない

- 状態：採用
- 決めた日：2026-09-16（PR #523をマージした日）
- 決めた人：45thのPM
- 決定の信頼度：記録なし
  - 根拠：#506とPR #523には、決めたことと、参照を確かめた結果は書かれているが、どれだけ確かだと思っていたかは書かれていない
- 出典：#506、PR #523

## 背景

GASからシフトを送ると、同じ名前のタスクが送るたびに増え続ける不具合があった（#506）。45thの本番では、36分間に同じ名前のタスクが2,504行作られていた。

直すときに、issueのチェックリストには「タスクを名前で引くとき（`FindByNames`）に、年度（year_id）で絞る」という案があった。年度で絞れば、前の年度の同じ名前のタスクを引かない。

ところが本番のtasksには、`postgresql/db/seed.sql`から入った行が、43年度のまま45thの運用データとして使われていた。

```text
id=1  空文字（未割当の印）   year_id=43  45th のシフト 12,289 件が参照
id=2  NG（参加不可の印）     year_id=43  45th のシフト  8,950 件が参照
id=3  タスク外               year_id=43  mobile のレスキュー送信に id が直書き
```

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 名前で引くときに、今の年度（45）で絞る | ほかの年度の同じ名前のタスクを引かない | id 1〜3を引けなくなる。GASの送信が45年度版の「空文字」や「NG」を新しく作り、既存の2万件のシフトは古い行を指したまま残る |
| 先に本番のid 1〜3のyear_idを今の年度にそろえてから、年度で絞る | 年度で絞れる | 本番データの書き換えが要る。mobileの直書きや、年度が変わるたびにそろえ直す作業も要る |
| 年度で絞らず、同じ名前が複数あるときはidの一番小さい（古い）行を使う | 本番データを変えずに直せる。seed由来の行はずっと同じidで使える | 前の年度に同じ名前のタスクがあると、それに紐づく |

## 決定

tasksのseed由来の行（空文字・NG・タスク外）は、年度をまたいで同じ行を使う。タスクを名前で引くときはyear_idで絞らず、同じ名前が複数あるときはidの一番小さい行を使う（PR #523）。

理由は`FindByNames`のコメントにも書いてある。

## 理由

年度で絞ると、本番で2万件のシフトが参照しているid 1〜2と、mobileが直書きで送るid 3を引けなくなるからである。本番データを書き換えずに増え続ける不具合を止めるには、絞らない方が安全だった。

seed.sqlは、DBを作り直しても、この3行を43年度で入れる。年度が変わっても、この3行は同じidと同じyear_idのまま残る。

## 前提

- 名前で引く処理は`api/lib/internals/repository/task_repository.go#taskRepository.FindByNames`
- シフトの送信は`api/lib/usecase/shift_usecase.go#shiftUseCase.UpdateShiftsFromGAS`、名前の正規化は`api/lib/usecase/shift_usecase.go#normalizeTaskName`
- seedの3行は`postgresql/db/seed.sql`
- mobileで、レスキューの「タスク外」をid 3で送るのは`mobile/lib/pages/rescue/rescue_request_tab/tab_pages/trouble.dart`
- 年度で絞りたくなったら、先にid 1〜3の扱い（year_idをそろえるか、年度に関係なく引く特別扱いにするか）を決め、mobileの直書きも直す。そのときは新しいADRを書く

## 結果

PR #523のマージ後、同じ名前のタスクが増え続ける不具合は止まった。
