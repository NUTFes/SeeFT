# 0004: PoC は試作用のブランチで試し、完成形が見えてから新しいブランチに持ち込む

- 状態：採用
- 決めた日：不明（2026 年前半、マニュアルの変換パイプラインの試作のころ）
- 決めた人：45th の PM
- 出典：理由の記録は PM の作業メモのみ（公開の出典なし）

## 背景

マニュアルを動画やスライドに変換する仕組みのように、作ってみないと形が分からないもの（PoC）を試すことがあった。こうした試作を、最初から develop に入れる前提のブランチで書くかどうかを決める必要があった。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 最初から develop から切ったブランチで、本番の品質で書く | そのまま PR にできる | 形が決まる前から本番の品質を求められて、手が止まる。試行錯誤のコミットが develop の履歴に流れる |
| 試作用のブランチで自由に試し、完成形が見えたら develop から新しいブランチを切って、要るファイルだけを持ち込む | 試す自由と、読みやすい PR を両立できる | 持ち込みの手間がかかる |

## 決定

PoC は試作用のブランチで自由に試す。新しい技術の検証も、同じ試作用のブランチに積んでよい。完成形が見えたら、develop から新しいブランチを切り、試作用のブランチから要るファイルだけを `git checkout <試作用のブランチ> -- <パス>` で持ち込んで PR にする。

持ち込む時期の目安は、「これは本番に入れる」と確信できたとき、または試作用のブランチが2か月を超えたとき。

ブランチ名に `spike/` のような種類を足すかは、決めていない。

## 理由

試作で散らかす自由と、マージのしやすさは、両立しにくい。形が見えないうちに develop 向けのブランチを切ると、本番の品質で書く必要が早く来すぎて、試作が進まない。逆に、完成してから新しいブランチに持ち込めば、試行錯誤のコミット（途中で捨てた方式の名残など）が develop の履歴に入らず、後から読める PR になる。
