# 0005: ほかの人の PR は、元のブランチに積んで引き継ぐ

- 状態：採用
- 決めた日：2026-09-20
- 決めた人：45th の PM
- 出典：#546（引き継いだ PR）、#545

## 背景

メンバーが作っていた PR（#546、レスキューの対応状況を Slack の DM で知らせる機能）を、PM が引き継いで仕上げることになった。引き継ぐときに要件も見直したので、作り直しに近い変更になった。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| develop から新しいブランチを切って新しい PR を作り、元の PR は閉じる | 新しい設計で、まっさらな PR を出せる | 議論・経緯・元の作者のコミットが、2つの PR に分かれる |
| 元の PR のブランチにコミットを積んで、同じ PR を育てる | 議論と経緯と作者のコミットが1つの PR に残る | 元のブランチが古いと、develop を取り込む手間がかかる |

## 決定

ほかの人の PR を引き継ぐときは、元の PR のブランチにコミットを積んで、同じ PR を育てる。

- 元のブランチが develop より古いときは、`git merge origin/develop` で取り込む。rebase して force push はしない
- PR の本文の冒頭に、引き継いだことと、方針を変えたならその理由を書く。作った人にもひと言コメントを残す

## 理由

1つの PR に、最初の議論から引き継いだ後の変更までが残るので、後から読む人が経緯を1か所でたどれる。元の作者のコミットも、その PR の中に残る。

develop を取り込むのに rebase を使わないのは、force push すると元の作者の手元のブランチと食い違うためである。develop へはスカッシュマージするので、merge で取り込んでも develop の履歴は汚れない。

[0004](0004-poc-spike-branch.md) の「新しいブランチに持ち込む」やり方は、自分の試作のためのもので、ほかの人の PR の引き継ぎには使わない。

## 前提

- develop へのマージはスカッシュマージ
- 決まりの本体は `docs/development/workflow.md` の9節

## 結果

#546 は、元の作者のコミットと PM のコミットが同じ PR に載ったままマージされた。PR の本文の冒頭に、引き継いだことと、要件を見直した理由（#545）が書いてある。
