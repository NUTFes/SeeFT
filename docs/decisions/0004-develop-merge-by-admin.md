# 0004: developの保護ルールを残したまま、PMがadmin権限で自分のPRをマージする

- 状態：採用
- 決めた日：不明（45thの途中から。この運用を記録したのは2026-09-14）
- 決めた人：45thのPM
- 決定の信頼度：記録なし
  - 根拠：この運用を始めたときの記録が無い。出典のPRは、この運用でマージした例で、決めたときの記録ではない
- 出典：PR #492、PR #512、PR #517、PR #548〜#564（この運用でマージしたPRの例）

## 背景

developには、GitHubのブランチ保護で「承認1件」と「PR上の会話がすべて解決していること」がマージの条件になっている。ただし「adminにも適用する」（enforce_admins）はオフで、admin権限を持つ人はこの条件を満たさなくてもマージできる。

45thの後半は、ほぼPMが1人で開発していた。PMのPRを承認できる、ほかのメンバーがいなかった。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 承認してくれる人が見つかるまで待つ | 保護ルールのとおりに進められる | 承認できる人がいないので、マージが止まる |
| ブランチ保護を外す | 誰でもすぐマージできる | メンバーのPRも、承認なしでマージできてしまう |
| 保護ルールを残し、PMだけadmin権限で承認0件のままマージする | メンバーのPRには保護ルールが適用されたまま、PMの作業は止まらない | PMのPRは人のレビューを受けない |

## 決定

developの保護ルールは外さない。PMはadmin権限で、承認0件のまま自分のPRをマージする。adminでない人のPRには、保護ルールがそのまま適用される。

PR上の会話（CodeRabbitのスレッドを含む）は、adminでも解決してからマージする。

## 理由

直接の理由は、PMのPRを承認できるメンバーがいなかったことである。

保護を外さなかった理由の記録は無い。メンバーのPRに承認を求める仕組みを残すため、というのは推測である。

人のレビューが無い分は、機械のレビューで補う方針をとった。lint（golangci-lint、flutter analyze）、CodeRabbit、コードの規約をAIにも読ませる`AGENTS.md`を重ねて、1人でも見落としを減らす。

## 前提

- ほぼ1人で開発していること。**複数人で開発するなら、このADRを見直す**（`docs/development/workflow.md`の7節は、複数人なら人のレビューを受けることを勧めている）
- developのブランチ保護が「承認1件・会話の解決・adminには適用しない」の設定であること。設定は`gh api repos/NUTFes/SeeFT/branches/develop/protection`で確かめられる
- 機械のレビューの設定は`.github/workflows/go-lint.yml`と`.coderabbit.yaml`

## 結果

2026年（9月末まで）にマージしたPR 127本のうち、作った人以外がレビューしたのは19本だった。2024〜2025年は、ほとんどのPRをほかの人がレビューしていた（2024年は32本中24本、2025年は27本中26本）。

人のレビューの代わりに、CodeRabbitの指摘で誤りが見つかった例がある（PR #564で3件、PR #568で3件）。一方で、CodeRabbitの枠（1時間に1回）を使い切っていて、指摘を直した後のコミットをCodeRabbitが見ないままマージした例もある（PR #568）。
