# 0004: develop の保護ルールを残したまま、PM が admin 権限で自分の PR をマージする

- 状態：採用
- 決めた日：不明（45th の途中から。この運用を記録したのは 2026-09-14）
- 決めた人：45th の PM
- 決定の信頼度：記録なし
  - 根拠：この運用を始めたときの記録が無い。出典の PR は、この運用でマージした例で、決めたときの記録ではない
- 出典：PR #492、PR #512、PR #517、PR #548〜#564（この運用でマージした PR の例）

## 背景

develop には、GitHub のブランチ保護で「承認1件」と「PR 上の会話がすべて解決していること」がマージの条件になっている。ただし「admin にも適用する」（enforce_admins）はオフで、admin 権限を持つ人はこの条件を飛ばしてマージできる。

45th の後半は、ほぼ PM が1人で開発していた。PM の PR を承認できる、ほかのメンバーがいなかった。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| 承認してくれる人が見つかるまで待つ | 保護ルールのとおりに進められる | 承認できる人がいないので、マージが止まる |
| ブランチ保護を外す | 誰でもすぐマージできる | メンバーの PR も、承認なしでマージできてしまう |
| 保護ルールを残し、PM だけ admin 権限で承認0件のままマージする | メンバーの PR には保護ルールが適用されたまま、PM の作業は止まらない | PM の PR は人のレビューを受けない |

## 決定

develop の保護ルールは外さない。PM は admin 権限で、承認0件のまま自分の PR をマージする。admin でない人の PR には、保護ルールがそのまま適用される。

PR 上の会話（CodeRabbit のスレッドを含む）は、admin でも解決してからマージする。

## 理由

直接の理由は、PM の PR を承認できるメンバーがいなかったことである。

保護を外さなかった理由の記録は無い。メンバーの PR に承認を求める仕組みを残すため、というのは推測である。

人のレビューが無い分は、機械のレビューで補う方針をとった。lint（golangci-lint、flutter analyze）、CodeRabbit、コードの規約を AI にも読ませる `AGENTS.md` を重ねて、1人でも見落としを減らす。

## 前提

- ほぼ1人で開発していること。**複数人で開発するなら、この ADR を見直す**（`docs/development/workflow.md` の7節は、複数人なら人のレビューを受けることを勧めている）
- develop のブランチ保護が「承認1件・会話の解決・admin には適用しない」の設定であること。設定は `gh api repos/NUTFes/SeeFT/branches/develop/protection` で確かめられる
- 機械のレビューの設定は `.github/workflows/go-lint.yml` と `.coderabbit.yaml`

## 結果

2026 年（9 月末まで）にマージした PR 127 本のうち、作った人以外がレビューしたのは 19 本だった。2024〜2025 年は、ほとんどの PR をほかの人がレビューしていた（2024 年は 32 本中 24 本、2025 年は 27 本中 26 本）。

人のレビューの代わりに、CodeRabbit の指摘で誤りが見つかった例がある（PR #564 で3件、PR #568 で3件）。一方で、CodeRabbit の枠（1時間に1回）を使い切っていて、指摘を直した後のコミットを CodeRabbit が見ないままマージした例もある（PR #568）。
