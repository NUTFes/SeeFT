# 判断の記録（ADR）

SeeFT のシステムと運用について、**何を決めたか**だけでなく、**なぜそう決めたか**と**何を選ばなかったか**を残す場所です。ADR（Architecture Decision Record）と呼ばれる書き方を使っています。

PR や issue には、採った案だけが残ります。MT の資料には結果しか書かれていないことが多く、方針の議論をした Slack は時間が経つと読めなくなります。後から「この作りは変えてよいのか」「前にこの案を見送ったのはなぜか」を判断するには、理由と、比べた候補が要ります。

## 何を ADR にするか

ADR にするのは、**システムの作りや本番の運用に関わり、後から戻すのに手間がかかる判断**です。

- 機能を足すと決めたとき。とくに、候補がいくつかあってその中から選んだとき
- 機能を見送った、先送りにしたとき。「やらない」と決めた理由は、後からいちばん分からなくなります
- 設計や構成を選んだとき（データの持ち方、通知の出し方、配信の仕方など）
- 運用の方針を決めたとき（本番の動かし方、年度の替わり目の扱いなど）
- [AGENTS.md](../../AGENTS.md) の「Ask First」に当たることを決めたとき
- やってみてうまくいかず、やめたとき

次のものは ADR にしません。

- **チームの約束事**（PR の書き方、点検のしかた、タスクの割り振り方、説明資料の組み方など）。すぐに変えられて、システムの作りには関わらないためです。[docs/development/workflow.md](../development/workflow.md) に、決まりと一緒に理由を短く書きます。変えるときは、その文書を直す PR に理由を書きます
- 選択肢が無かったバグ修正や、PR の本文で説明が足りるもの

迷ったら、「1年後に後任がこれを変えようとしたとき、理由を知らないと困るか」で決めてください。

## 決める前に書く

ADR は、決めた後の記録であると同時に、決めるための資料にもなります。候補を比べて決める判断は、**決める前に**状態を「提案」にして書き、PR に出します。

1. 背景と候補と、推す案を書き、状態を「提案」にして PR を出す
2. PR の上で議論する。候補が増えたら表に足す
3. 決まったら状態を「採用」か「見送り」にして、決めた日と決めた人を書き、マージする

[AGENTS.md](../../AGENTS.md) の「Ask First」に当たる変更は、実装の前にこの流れで進めます。実装と同じ PR に入れても構いません。

後から過去の判断を起こすときは、最初から「採用」などの状態で書きます。

## 書き方

[template.md](template.md) をコピーして、`NNNN-題.md` の名前で置きます。番号は4桁の連番、題は英小文字とハイフンです（例：`0003-slack-dm-notification.md`）。書いたら、下の「一覧」に1行足してください。

**確信度を書きます。** 確信が低いまま決めることもあります。低いと書いておけば、後任が見直すきっかけになります。低いときは、何が分かれば見直すかを「前提」に書きます。

**理由が分からないときは「理由の記録なし」と書きます。** 過去の判断を後から起こすときは、理由が残っていないことがよくあります。推測で埋めると、後の人は推測を事実として読みます。推測を書くときは、推測だと明記してください。

**本文は書き換えず、追記します。** 書いた後で変えてよいのは、「状態」の行、末尾の「追記」、誤字、それにコードの名前やパスだけが変わったときの「前提」欄の参照先です（下の「前提と、前提の点検」）。判断が変わったら、新しい番号で ADR を書き、古い方の状態を `置き換え（→ NNNN）` にします。古い判断とその理由は、そのまま残します。

状態は次のどれかです。

| 状態 | 意味 |
| --- | --- |
| 提案 | まだ決まっていない |
| 採用 | 決めて、実際にそうしている |
| 見送り | やらないと決めた（先送りも含む） |
| 撤回 | 一度採用したが、やめた |
| 置き換え（→ NNNN） | 新しい ADR に置き換わった |

## 前提と、前提の点検

「前提」の欄には、その判断が成り立つための条件を書きます。コードを前提にした判断なら、どのファイルのどの関数かを書きます。

コード上の前提は、PR ごとに CI（`.github/workflows/docs-refcheck.yml`）が確かめます。ファイルが消えたり、関数の名前が変わったりすると CI が落ちるので、前提が古くなったことに気づけます。点検の対象になるのは、インラインコード（バッククォートで囲んだ部分）に次の形で書いたものです。

<!-- refcheck:off -->
| 書くもの | 書き方 | 例 |
| --- | --- | --- |
| ファイル | リポジトリのルートからのパス。先頭に `./` や `/` を付けない | `api/lib/usecase/shift_usecase.go` |
| ディレクトリ | 末尾に `/` | `docs/operations/` |
| 関数・型・定数 | ファイルのパスと `#` でつなぐ | `gas/shift/コード.js#YEAR_ID` |
| メソッド | `#型.メソッド` | `api/lib/usecase/shift_usecase.go#shiftUseCase.UpdateShiftsFromGAS` |
<!-- refcheck:on -->

- **行番号は書きません。** `shift_usecase.go:1026` のような書き方は、コードが1行ずれただけで古くなるので、CI がエラーにします。関数や定数の名前で指してください。
- 関数などは、そのファイルの中に名前が単語として現れるかだけを確かめます。定義の中身までは見ません。
- 1段目がリポジトリの直下に無いもの（`application/json` など）、`.gitignore` で管理から外したもの（`.env` など）、`~` や `/` で始まるもの、`*` `?` `{` `}` `<` `>` を含むもの、コードブロックの中は点検しません。
- 実在しないパスを例として書くときは、その行の末尾に `<!-- refcheck:ignore -->` を付けるか、範囲を `<!-- refcheck:off -->` と `<!-- refcheck:on -->` で挟みます。

CI が落ちたら、前提が本当に崩れたのかを確かめます。

- **名前やパスが変わっただけで、判断は変わらない**：前提欄のパスを直し、追記に日付と理由を1行書きます
- **判断の前提が崩れた**：新しい ADR を書くか、今の ADR の状態を変えます

手元でも同じ点検ができます。

```bash
python3 scripts/refcheck/refcheck.py docs/decisions/*.md
```

## 公開リポジトリなので書かないもの

このリポジトリは公開されています。次のものは ADR に書かず、非公開の場所で扱います。

- 個人名。人は役職で書きます（「45th の PM」「執行部」など）
- スプレッドシートや Drive の ID、アカウント、秘密の値
- サーバーの IP アドレスや経路
- まだ直っていないセキュリティの問題（GitHub の非公開のセキュリティアドバイザリで扱います）

出典に MT の資料や議事録を挙げるときは、リンクを貼って構いません。閲覧に招待が要るものは、そう書き添えてください。
