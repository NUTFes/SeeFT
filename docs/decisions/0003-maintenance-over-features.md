# 0003: SeeFT 本体は新しい機能を足さず、保守性を上げる

- 状態：採用
- 決めた日：2026-07-06（MT の日。#391 の本文）
- 決めた人：45th の SeeFT の MT
- 決定の信頼度：記録なし
  - 根拠：#391 と `docs/development/test-roadmap.md` には、決めたことは書かれているが、どれだけ確かだと思っていたかは書かれていない。理由が書かれているはずの MT の資料は、まだ読めていない
- 出典：#391、`docs/development/test-roadmap.md`、2026-07-06 の SeeFT の MT の資料（Notion。閲覧にはワークスペースへの招待が要る。この ADR を書いた時点では未確認）

## 背景

2026 年 7 月の時点で、SeeFT はほぼ PM 1人で開発していた。`api/` のテストは0件で、CI は lint だけだった。直したつもりで別の場所を壊しても、気づく手段が無かった。

一方で、技大祭の運営で手間がかかっていたのは、SeeFT に載せる情報（シフト・タスク・マニュアル）を作る側だった。7月6日の MT で、SeeFT 本体の今後をどうするかを話し合った。

## 候補

| 候補 | 良い点 | 悪い点 |
| --- | --- | --- |
| これまでどおり、本体に新しい機能を足していく | 参加者から見える改善が増える | テストが無いまま変更が増え、壊れても気づけない。1人では手が回らない |
| 本体は新しい機能を足さず、保守性を上げる。手間は「載せる情報を作る側」の支援に向ける | 壊さずに直せるようになる。運営の一番重い手間に手が届く | 参加者から見える変化は少ない |

MT で比べたほかの案があったかは、MT の資料を読めていないので分からない。

## 決定

SeeFT 本体（mobile・api・admin）は、新しい機能を足さず、保守性を上げる方向に振る。直す前にテストを書いて今の動作を正解として固定し、その安全網の中で直す。主な手間は、SeeFT に載せる情報を作る側（スプレッドシート・GAS・マニュアルの生成）の支援に向ける。

テストの進め方は `docs/development/test-roadmap.md` にまとめた（#391）。

## 理由

ほぼ1人の開発体制で、壊さずに直すためである。テストが無い状態でコードを書き換えると、直したのか壊したのかを判定できない。

手間を「作る側」に向けた理由の詳しい議論は、MT の資料にある（未確認）。

## 前提

- テストの進め方の本体は `docs/development/test-roadmap.md`
- 開発の人数が少ないこと。人数が増えて、新しい機能とテストを並行できるなら、見直してよい

## 結果

技大祭までに、技大祭に要る機能を優先して足した。

- シフト変更の Slack 通知（#476・PR #522）
- 休憩カード（#488・PR #492）
- マニュアルの配信（#444・PR #445）
- レスキューの対応状況の通知（PR #546）

テストは、フェーズ0（CI で `go test` を実行する、Go のバージョンをそろえる）が済み、`api/` のテストのファイルは 18 本になった。一方、メンバーに割り振ったフェーズ1のテスト（#420〜#424）は、2026-09-30 の時点で1件もマージされていない。

45th の PM は、方針が間違っていたというより、技大祭という締切の前では機能の要求が方針に勝った、と振り返っている。同じ方針を続けるなら、締切の前に何を足さないかまで決めておく必要がある。
