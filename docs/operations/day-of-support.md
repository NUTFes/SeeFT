# 当日の問い合わせ対応

技大祭の期間中（準々備日〜片付け日）に、委員から SeeFT について問い合わせを受けたときの手引きである。症状ごとに、最初に何を見るかを書く。45th（2026年）に実際に受けた問い合わせと、そのときの調べ方から書いた。

45th で分かったのは、**問い合わせの多くはシステムの故障ではなかった**ということである。スプシの編集がそのまま送られた、アプリが古いデータを表示していた、「失敗」と出たが実際には届いていた、というものが多い。直す前に、まず何が起きたかを確かめる。

## 最初に見る場所

| 見る場所 | 分かること | 見方 |
| --- | --- | --- |
| `https://seeft-api.nutfes.net` をブラウザで開く | 本番が動いているか | 下の「アプリが開かない」 |
| DB | 名簿・シフト・通知・レスキューの実際の中身 | 入り方は別紙。この文書の SQL はすべて読むだけのもの |
| API のログ | レスキューの転記の成否、エラー | 本番サーバーで `docker logs` |
| シフトスプシ・レスキュースプシ | 誰がいつ何を変えたか | 変更履歴、GAS の「実行数」 |

### 時刻の読み方

同じできごとでも、見る場所によって時刻の基準が違う。取り違えると、原因を別の送信と結びつけてしまう。

| 場所 | 時刻の基準 |
| --- | --- |
| API のログ、`docker inspect` | UTC（日本時間は9時間足す） |
| Apps Script の「実行数」、Slack | 見ている人のタイムゾーンの設定 |
| DB（`timestamptz` の列） | 接続した psql のタイムゾーン。日本時間で見るなら `SET TIME ZONE 'Asia/Tokyo';` |

## 症状別

### アプリが開かない、すべての画面でエラーになる

ブラウザで `https://seeft-api.nutfes.net` を開き、Cloudflare のエラー番号を見る。1033 ならサーバーごと止まっている、502 なら API だけが止まっている。復旧の手順は [本番へのデプロイ](deploy.md) の「止まったときの復旧」にある。

特定の人だけが開けず、アドレスバーが `/layout` などになっている場合は、トップ（`https://seeft.nutfes.net/`）から開き直してもらう。再読み込みで404になる不具合は #512 で直したが、古いアプリ本体が残っている端末では起きうる。

### ログインできない

アプリのエラー表示は原因を区別しない。本人がいない、パスワードが違う、サーバーのエラー、のどれでも同じ表示になる。DB で本人がいるかを確かめる。

```sql
SELECT id, name, student_number FROM users WHERE student_number = <学籍番号>;
```

| 結果 | 考えられること |
| --- | --- |
| 行がない | 名簿送信に入っていない。途中参加で「メンバーを追加」がまだ、または名簿作成アンケートに回答がない |
| 行がある | パスワードの入力違い。初期パスワードは説明会で伝えた値である |
| 全員ログインできない | サーバーの停止か、名簿の学籍番号の誤り（45th は全員0で送られていた） |

### シフトがスプシと違う、古い

2つの可能性がある。スプシを編集したあとに送信していない場合と、アプリが古いデータを表示している場合である。

DB のシフトがいつ書かれたかを日程ごとに見る。

```sql
SELECT date_id, count(*) FILTER (WHERE updated_at >= CURRENT_DATE) AS touched_today, count(*) AS total, max(updated_at) AS last_write FROM shifts WHERE weather_id = 1 GROUP BY date_id ORDER BY date_id;
```

`last_write` がスプシを編集した時刻より前なら、送信がまだである。シフトスプシの SeeFT メニューから送る。GAS の「送信が完了しました」は、DB がシートと同じであることの証明にならない。

DB が新しいのにアプリが古い場合、アプリは前回取得したシフトを先に表示している。アプリを開き直してもらう。

### 準々備日・片付け日・雨のシフトが見えない

45th のアプリは、準備日・1日目・2日目の晴れのシフトしか表示しない。準々備日と片付け日を送っても、アプリには出ない。見せるにはアプリの改修が要る（[SeeFT に渡すデータの約束事](seeft-data-contract.md) の「年度が変わるときに直すところ」）。

### 何もしていないのに通知が来た

**本人は何もしていなくても、シフトを作る側がスプシを編集して送れば通知は届く。** 45th の準備日には、配らないことになった食事の枠が一括で空欄にされて送られ、数百人に通知が届いた。

通知の中身と、いつ作られたかを見る。

```sql
SELECT a.created_at, a.action_type, a.is_sent, a.diff_payload FROM action_logs a JOIN users u ON u.id = a.user_id WHERE u.student_number = <学籍番号> ORDER BY a.created_at DESC LIMIT 20;
```

- 「→（割り当てなし）」は、その枠が空欄に変わったという意味である。45th の準備日までは同じ意味で「→（不明）」と表示されていた。
- 作られた時刻の前後に、シフトスプシの送信（GAS の「実行数」）があるはずである。どのセルを誰が変えたかは、シフトスプシの変更履歴で分かる。

### 通知が来ない

順に確かめる。

1. **Slack ID が登録されているか。** 名簿送信のときに、技大祭メールで Slack のユーザーを引いている。Slack に登録したメールが違うと引けない。

```sql
SELECT name, mail, slack_user_id FROM users WHERE student_number = <学籍番号>;
```

`slack_user_id` が空なら、シフトスプシの `SlackID` シートに手で行を足して、名簿を送り直す。

2. **本当に変更があったか。** 通知は変更があったときだけ届く。Slack 通知を有効にする前から DB にあったシフトは、通知されない。45th には「調理場のシフトが通知されない」という問い合わせがあったが、そのシフトは通知を有効にする前から入っていた。

3. **5分待ったか。** 通知は5分おきにまとめて送られる。

4. **送信で失敗していないか。** 1人の1日分の変更が多すぎると（1通の上限は3,000字）Slack が受け付けない。その分は既読にならないまま毎回失敗し、その人への以後の通知も止まる。45th では起きなかった（見積もりの最大は約2,000字）。API のログで Slack のエラーを探す。

### マニュアルのボタンがない、開かない

| 症状 | 原因と対処 |
| --- | --- |
| ボタンがない | タスクにマニュアルが紐付いていない。シフトスプシの「【事前確認】マニュアルURLの紐付けを点検する」で確かめ、直したらタスクを送る。**マニュアルが実在していても、紐付けの表に行がないと出ない**（[事故の記録](incidents-45th.md)） |
| Google のエラーや「アクセス権が必要」が出る | ドキュメント版（PDF）は技大祭アカウントに閲覧を限定している。スマホのブラウザで、技大祭アカウントで Google にログインしてもらう |
| 解説 HTML がログイン画面になる | 解説 HTML も技大祭アカウントに限定している。技大祭アカウントを選んでログインしてもらう |
| 2日目なのに1日目のマニュアルが開く | 1日目と2日目で同じ名前のタスクは、マニュアルが1つにまとめられる。日ごとに名前を分けないと直らない |

### レスキューで「送信に失敗しました」と出た

**失敗と出ても、届いていることがある。** 45th では、失敗の表示を見た人が押し直して、同じレスキューが2〜3件届いた。押し直してもらう前に、届いているかを確かめる。

```sql
SELECT id, user_id, status, created_at FROM question_rescues ORDER BY id DESC LIMIT 5;
```

トラブルは `trouble_rescues`、人が来ないは `shorthanded_rescues` を見る。DB に行があれば、レスキュースプシにも行があるかを確かめる。

スプシへの転記が失敗したかどうかは、API のログで分かる（時刻は UTC で指定する）。

```bash
docker logs --since <UTC時刻> nutfes-seeft-api 2>&1 | grep "GAS送信"
```

同じ人が同じ内容を180秒以内に送った分は、GAS が1件にまとめ、重複した側を「対応番号Xにまとめました」として閉じる。

### レスキューの返答がアプリに出ない

- 対応状況と返答を書く列はシートで違う。質問は I・J 列、トラブルと人が来ないは K・L 列。各シートの1行目の「↓ここを記入」が目印である。
- 対応番号（A 列）を書き換えると、返答が別のレスキューに届く。書き換えていないかを見る。
- 返答をアプリに戻すのは、レスキュースプシのインストール型トリガー（`onChange`）である。動いたかは Apps Script の「実行数」で見る。
- 対応番号が空の行を編集すると404のダイアログが出るが、害はない。

### レビューを求める画面が何度も出る

古いアプリ本体が端末に残っていると起きる（45th の準備日にあった）。ページを再読み込みしてもらう。

## DB を調べるときの注意

この文書の SQL はどれも読むだけである。**当日に DB を書き換えることは、原則として避ける。** どうしても直すときは、次を守る。

- 接続が切れていると、`BEGIN` が飲み込まれ、そのあとの `DELETE` や `UPDATE` が即座に確定することがある。45th では、`BEGIN; DELETE …; COMMIT;` をまとめて貼ったときにこれが起きた。
- `BEGIN;` は**単独で**打ち、プロンプトが `=*>` のように `*` 付きになったことを見てから次に進む。
- psql の表示を結果の証拠にしない。45th では `DELETE 0` と表示されたのに、実際には4件消えていた。別の方法で件数を確かめる。
- タスクの `url` や `manual_url` を SQL で書き換えても、次のタスク送信で上書きされる。直すのはスプシの側である。

## 説明会で伝えておくと減る問い合わせ

- 初期パスワードと、ログインは学籍番号で行うこと
- アプリはトップ（`https://seeft.nutfes.net/`）から開くこと
- マニュアルを開くには、スマホのブラウザで技大祭アカウントにログインしておくこと
- レスキューで「送信に失敗しました」と出ても、すぐには押し直さないこと
- 通知の「→（割り当てなし）」は、その時間の割り当てが外れたという意味であること
- アプリに出るのは準備日・1日目・2日目のシフトだけであること（45th の場合）
