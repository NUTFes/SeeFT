## スプシ

### 希望調査の参加不可が別人の行にずれた（8/8〜8/15）

- **何が起きたか**：委員から「自分に入るはずのないシフトが入っている」と報告があった。本人が黒塗りした参加不可が、別の人の行に移っていた。
- **原因**：執行部がマスター名簿を並べ替えた。希望調査の名前の列は IMPORTRANGE で並べ替えに追従するが、本人が塗った黒塗りは行に固定されている。名前だけが動き、黒塗りが取り残された。並べ替えはマスター側の操作なので、**希望調査の変更履歴には何も残らなかった**。
- **対処**：マスター名簿に固定名簿（シート保護付き）を作り、局別シートはそこから引くようにした。全体名簿は自由に並べ替えてよくなった。ずれた期間の入力は、変更履歴を1件ずつ辿って本人の行へ戻した。
- **教訓**：別シートどうしを行番号で暗黙に対応させない。また、変更履歴で数式セル（IMPORTRANGE や QUERY）の表示を見ても、当時の値とは限らない。信用できるのは、手で入力されたセルの行番号と編集者名だけである。

### 日程シートが一面真っ赤になった（8/26・8/27）

- **何が起きたか**：情報局長から「準備日以降が真っ赤」と報告があった。シフトのデータ自体は無傷だった。
- **原因**：4段の連鎖である。①タスク一覧は8局の IMPORTRANGE を縦に積んでおり、1局でも読み込み中だと全体が `#VALUE!` になる。②日別タスクは IFERROR でそのエラーを握りつぶし、空のリストを返す。③日程シートには「日別タスクにないタスクを赤くする」条件付き書式がある。④リストが空なので、入力済みの全セルが赤になった。
- **対処**：各局の IMPORTRANGE を IFERROR で包み、1局が欠けても全体は消えないようにした。
- **残っていること**：局のファイルを編集している間は、その局のタスクだけが一時的に欠けて赤く見える。条件付き書式に「リストが空なら警告しない」という条件を足せば消えるが、未実施。
- **教訓**：「リストになければ異常」という形の警告は、リストが空になると全件を異常と判定する。

### 開店・閉店チェックのマニュアルボタンが消えた（9/18）

- **何が起きたか**：準備日のタスク送信で、開店・閉店チェック4タスクのマニュアル（PDF）のボタンが消えた。
- **原因**：総務局のタスクファイルで、この8行の M 列（マニュアル名）が「参加団体部門」に書き換わっていた。マニュアルURLシートとの照合が外れ、空欄が送られた。誰がいつ変えたかは、総務局のタスクファイルの変更履歴でしか分からない。
- **もう1つの問題**：このタスクは1日目と2日目で同じ名前である。タスク送信は同じ名前を先勝ちで1件にまとめるので、もともと2日目にも1日目のマニュアルが開く状態だった。直すには、日ごとにタスク名を分ける必要がある。

### 実在するマニュアル4本が、アプリから辿れなかった（技大祭後に判明）

- **何が起きたか**：アプリ内レビューで「マニュアルがない」とされたタスクのうち4つ（物品貸出・物品移動・テント設営の人員移動）は、ドキュメントが実在していた。
- **原因**：タスクファイルの M 列にはマニュアル名があったが、マニュアル割り当てスプシにもマニュアルURLシートにも行がなかった。**割り当てスプシの外で作られたマニュアル**だったので、紐付けの流れに乗らなかった。
- **教訓**：点検コマンドの「不足」は「まだ作られていないマニュアル」とは限らない。実在するのに登録されていないものが大半だった。現場は公式の流れの外でもマニュアルを作っている。

## スプシから API へ

### 本番の全員が学籍番号0で、誰もログインできなかった（8/26）

- **原因**：名簿送信の GAS が、学籍番号として常に `0` を送っていた。API は0をそのまま受け入れ、エラーを出さなかった。
- **対処**：名簿作成アンケートの回答から名前で学籍番号を引くようにした。8桁でない人がいると、送信全体を止める。
- **教訓**：API が既定値で受け入れてしまう項目は、送る側で止めるしかない。

### シフト送信が6分の制限で落ち続けた（9/5）

- **原因**：2つ重なっていた。①`shifts` テーブルに主キー以外のインデックスがなく、1件ごとに全行を読んでいた。②GAS が6分で打ち切られても API は処理を続けていたため、次の実行を重ねると同じ行を奪い合った。
- **対処**：本番にインデックスを手で貼った（issue #500。migration には未収録）。止まっても連打せず、数分空けて DB の件数を確かめる運用にした。**止まったように見えても、DB には最後まで入っていることがあった。**
- **残っていること**：送信を一括の SQL にまとめる改修（issue #501）。

### 同じ名前のタスクが2,504行できた（9/6）

- **原因**：`Music Nuts　参加`（全角スペース入り）のタスク名が、タスク送信より先にシフト送信で届いた。API は照合のときだけ全角を半角にそろえ、作るときは元の名前で作るので、送るたびに新しく作り続けた。
- **対処**：9/16 に、どこからも参照されていないことを確かめてから削除した。以後、名簿 → タスク → シフトの順を守った。
- **残っていること**：コードの修正（issue #506）。

### 名前の行の壊れたセルで、シフト送信が途中で失敗した（9/17）

- **原因**：2日目の日程シートの名前行に、壊れた文字列のセルがあった。API は名簿にない名前を受け取ると、その回の1,000件のかたまりをエラーにする。20,001件目以降が HTTP 500 で止まった。
- **対処**：セルを直して送り直した。送信前に「【事前確認】名前がDBに全部あるか調べる」を回せば防げた。

### レスキューの電話番号と時刻（9/17、往復テストで発見）

- **電話番号の先頭0が落ちた**：GAS の `appendRow` が数字だけの文字列を数値として書き込むため、`090…` が `90…` になった。対処はアポストロフィを付けてテキストとして書き込むこと。列の表示形式を変えても直らない（テーブルの型付き列のため）。
- **アプリの発生時刻が9時間ずれた**：API が UTC のまま返していた（#535 で修正）。
- **採番の競合**：同時に送られると同じ番号を取りうる作りだった（#536 で修正）。
- **GAS の送り先の誤り**：GAS の `API_BASE_URL` が、API ではなくアプリの配信元を指していた。末尾にスラッシュがあると URL が `//` になって404になる。どちらも**失敗が画面に出ない**。GAS の実行履歴でしか気づけない。

### レスキューが2〜3件ずつ重複して届いた（9/19）

- **何が起きたか**：同じ内容のレスキューが、16〜43秒おきに2〜3件届いた。
- **原因**：GAS のウェブアプリは、書き込みが終わったあと2段階で応答を返す（POST への 302、続いて結果を取りに行く GET）。この2段階目が、Google 側で数分間だけ404を返す時間帯があった。API はそれを失敗と判定し、アプリに「送信に失敗しました」と表示した。スプシには書き込めていたので、押し直した分が重複になった。
- **対処**：API は302を受けた時点で成功とし、結果を取りに行かないようにした（#548）。GAS 側でも、180秒以内の同じ送信を1件にまとめるようにした（ウェブアプリのバージョン4）。
- **教訓**：「送信に失敗しました」は、届いていないことの証明にならない。「送れない」と言われたら、先に DB を見る。

## 運用

### 参加不可の申告と既存の割り当てが重なった（8/26〜8/27）

- **何が起きたか**：準備日を中心に、参加不可を申告した時間帯にシフトが入っている人がいた（準備日だけで19人）。準備日は平日で、授業や研究の申告が多い。
- **原因**：割り当てのあとに申告された、または割り当てた人が黒塗りを見ていなかった。
- **対処**：「参加不可の警告を更新」を実行し、黒塗りに重なった割り当て2,066件を自動で取り消した。取り消した分はシフトの穴になるので、割り当てる側（執行部）に人数チェックで穴を確かめてもらう必要があった。
- **教訓**：取り消しは大量に起きる。実行する前に執行部へ知らせ、スプシの版を保存しておく。

### 数百人に「→（不明）」の通知が届いた（9/18）

- **何が起きたか**：「何も変えていないのに通知が来た」と問い合わせがあった。
- **原因**：シフトを作る側が、配らないことになった食事の枠をスプシで一括で空欄にし、送信した。空欄への変更は、通知で「〇〇 → （不明）」と表示されていた。システムの誤作動ではなかった。準備日の夕食だけで192人・619コマが対象だった。
- **対処**：空欄を「（割り当てなし）」と表示するよう直した（#544）。すでに作られていた通知の文面は変わらない。
- **残っていること**：送信の前に「何件変わり、何人に通知が飛ぶか」を見る手段がない。

## デプロイとアプリ

### 本番の API が古いビルドのままだった（8/28）

- **原因**：本番の Dockerfile はソースをイメージに焼き込むので、サーバーで `git pull` しただけでは反映されない。ビルドが漏れていた。API の応答に新しい項目名が含まれていたため、新しいビルドだと誤認した。
- **対処**：ビルドし直して反映した。**動いているコードは、コンテナの中のファイルを見て確かめる。**

### マニュアルを開くと Google のエラーが出た（9/13）

- **原因**：アプリはドキュメントを埋め込みの枠で開いていた。閲覧を技大祭アカウントに限定したファイルは、Google のログイン情報が届かない他サイトの枠では開けない。PDF にしたことは原因ではなかった。
- **対処**：常に別のタブで開くようにした（#510）。

### アプリを再読み込みすると404になった（9/13）

- **原因**：ログイン後の URL が `/layout` になるが、本番でアプリを配信している Python のサーバーが、存在しないパスに `index.html` を返していなかった。2023年からある不具合で、再読み込みしたときだけ起きる。
- **対処**：拡張子のないパスには `index.html` を返すようにした（#512）。

### トラブルの発生場所と詳細が入れ替わって届いた（9/19）

- **原因**：アプリのコードで、同じ型（文字列）の引数を2つ、逆の順番で渡していた。コンパイラは検出しない。
- **対処**：名前付き引数にした（#552）。

## インフラ

### 本番が約3時間止まり、自動で復帰しなかった（9/15 未明）

- **何が起きたか**：本番サーバーの載っている物理ノードが、インフラ側のメンテナンスで止まった。SeeFT のコードやデプロイとは無関係だった。
- **原因**：ノードが復帰しても、本番のコンテナ（CT）が自動起動する設定になっておらず、Docker のコンテナにも再起動の設定がなかった。復旧に3段階の手作業が要った。
- **残っていること**：CT の自動起動と、`docker-compose.prod.yml` の `restart: unless-stopped`。どちらも未実施。
- **切り分けの勘所**：Cloudflare が 1033 を返すときはトンネル（cloudflared）自体が落ちている。502 なら、トンネルは生きていて API が落ちている。

## 共通する原因

並べてみると、事故の多くは**スプシから API へデータが渡る境目**で起きている。学籍番号0、重複タスク、壊れた名前、マニュアル名の不一致、電話番号の0、場所と詳細の入れ替わりがそうである。スプシは毎年人の手で作り直されるので、46th でも同じ種類の事故が形を変えて起きると考えたほうがよい。

もう1つの共通点は、**失敗が画面に出ない**ことである。VLOOKUP の不一致は空欄になるだけ、GAS のトリガーの失敗は実行履歴にしか出ない、API は知らないタスク名を黙って作る、「送信に失敗しました」でも実際には届いている。

46th で既存機能を改善するときは、次の2点から考えるとよい。

- 境目の確認を API 側に寄せる。スプシが誰にどう作られても、壊れたデータは API が弾き、何が悪いかを返す。
- 一括の送信・通知の前に、何件変わり、何人に通知が飛ぶかを見せる。
